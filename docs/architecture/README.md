# Picorer Architecture

Picorer is a domain-oriented modular monolith. Top-level modules describe product capabilities; ports and adapters isolate external technologies inside each capability.

## Contexts

| Context | Owns | Must not own |
|---|---|---|
| `memory` | Immutable source memories, scopes, sessions, ingest, exact reads | Ranking, citations, dataset labels |
| `retrieval` | Search requests, hits, ranking, embeddings, temporal and numeric facts | Agent protocol, citations, evaluation labels |
| `evidence-agent` | Search/read/finish protocol, ledger, exact-evidence retention, harness-owned citations | Evaluation-specific answer formatting and scoring |
| `agent-runtime` | Stateful Pi Agent loop that interleaves memory tools with caller-owned environment tools | Environment action execution and evaluation |
| `benchmark` | Questions, answer stage, durable runs, retry, artifacts, evaluation | Raw-memory or retrieval implementation details |

`entrypoints` parses external input. `composition` is the only module that wires concrete adapters together. `platform` contains technology adapters shared by more than one context and must not contain domain policy.

## Source Map

```text
src/
|-- memory/                 immutable source-memory models, ingest use case, and store port
|-- retrieval/              search orchestration, ranking, operators, embedding model, and adapters
|-- evidence-agent/         evidence ledger, Pi tools, prompts, and bounded agent runtime
|-- agent-runtime/          interactive memory-agent session over caller-owned tools
|-- benchmark/              dataset adapters, label firewall, answer/evaluation policy, and benchmark wiring
|-- entrypoints/cli/        argument parsing, command handlers, and the CLI router
|-- composition/            generic construction of concrete Picorer adapters
|-- platform/               SQLite, Pi SDK, filesystem, security, and concurrency adapters
|-- util.ts                 small technology-neutral shared helpers
`-- {cli,*-api,*-bridge}.ts stable executable build shims only
```

## Dependency Direction

```text
entrypoints   -> composition
benchmark     -> agent-runtime -> evidence-agent -> retrieval -> memory
benchmark     ----------------> evidence-agent -> retrieval -> memory

adapters -> ports/use-cases/model in the same context
composition -> concrete adapters
```

Dependencies point toward stable policy. Database rows, Pi SDK messages, OpenAI payloads, Docker arguments, and filesystem layouts stay in adapters.

The structure applies Parnas-style information hiding at file boundaries, DDD bounded contexts at capability boundaries, and ports-and-adapters for technology boundaries. Characterization tests preserve observable behavior while old source-level compatibility facades have been removed.

## File Rule

A file owns one reason to change, not necessarily one function. Functions stay together when they implement the same policy and have the same dependencies and test strategy. Split a file when its contents change for different reasons or require different external technologies.
